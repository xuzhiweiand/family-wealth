### 1.3 关键设计原则

| 原则         | 含义                            | 体现                           |
| ---------- | ----------------------------- | ---------------------------- |
| **本地优先**   | UI 永远从本地 SQLite 读，0 阻塞        | 启动 < 800ms 可展示数据             |
| **E2E 加密** | 金额字段服务端看不到明文                  | AES-256-GCM + Per-Family DEK |
| **客户端聚合**  | 趋势图不依赖服务端 SQL                 | 见 [数据模型 §6](./数据模型设计.md)     |
| **离线可用**   | 飞行模式下完整 CRUD                  | 双向同步 + 冲突解决                  |
| **薄后端**    | 90% 逻辑在客户端                    | Edge Function 只做客户端做不了的事     |
| **类型驱动开发** | TypeScript strict + Zod 运行时校验 | 编译期拦截 80% Bug                |

### 1.4 数据流（按典型场景）

**场景 A：录入一条资产**

```
用户填写表单
  → 表单 Zod 校验（客户端）
    → 计算新 amount，生成 snapshot
      → 加密（amount + payload）→ 写本地 SQLite
        → 写 sync_queue 表（标记 dirty=true）
          → 后台 Supabase upsert（含 RLS 鉴权）
            → 成功则标记 dirty=false；失败则指数退避重试
```

**场景 B：B 用户的 C 设备收到 A 用户录入的消息**

```
Realtime 推送 INSERT 到 assets 表
  → Edge Function 验证 family_id + 权限（防越权；客户端也校验一次）
    → 客户端收到 encrypted blob
      → 用本地缓存的 Family Data Key 解密
        → 写本地 SQLite
          → Zustand store 通知 UI 重渲染
```

## 2. 技术栈选型

> 选型原则：**成熟 + 生态完整 + TypeScript 一等公民**。能跑就行，不追新。


### 2.1 客户端

| 层     | 选型                                                                    | 版本                    | 备选                    | 选 / 不选理由                                           |
| ----- | --------------------------------------------------------------------- | --------------------- | --------------------- | -------------------------------------------------- |
| 框架    | **React Native + Expo**                                               | Expo SDK 52 / RN 0.76 | Flutter / 原生          | 与 Web 工具链共通；Expo Dev 构建 = 云端 EAS；OTA 热更新；AI 工具链最成熟 |
| 语言    | **TypeScript（strict）**                                                | 5.4+                  | —                     | 端到端类型；Data Model 已出 TS 类型                          |
| 路由    | **Expo Router**                                                       | 5.x                   | React Navigation      | 文件路由 + 深度链接 + SSR-ready；新项目首选                      |
| 状态管理  | **Zustand**                                                           | 5.x                   | Redux Toolkit / Jotai | 轻量、无 boilerplate、与 React Query 互补                  |
| 远端状态  | **TanStack Query v5**                                                 | 5.x                   | SWR                   | 与 Zustand 分工清晰；自动 refetch / 乐观更新 / 失效              |
| 本地数据库 | **WatermelonDB**（主）/ **expo-sqlite**                                  | latest                | MMKV / AsyncStorage   | WatermelonDB 同步模型天然适合「本地优先 + 后台同步」；expo-sqlite 作降级 |
| 表单    | **React Hook Form + Zod**                                             | latest                | Formik                | 性能 + 类型校验结合最干净                                     |
| UI 库  | **Tamagui** 或 **NativeWind v4**                                       | —                     | —                     | 决定中：见 [§22 待决策清单](#22-附录待决策清单决策矩阵)                 |
| 图表    | **Victory Native XL** 或 **react-native-gifted-charts**                | —                     | —                     | 性能优于 react-native-chart-kit；趋势图核心                  |
| 加密    | **react-native-quick-crypto** 或 **@noble/ciphers**                    | —                     | —                     | 见 [§11.3](#113-加密库选型)                              |
| OCR   | **Apple Vision** (iOS) + **Google ML Kit Text Recognition** (Android) | —                     | Tesseract             | 原生精度 95%+，比 Tesseract 快 5-10×                      |
| 推送    | **expo-notifications**                                                | —                     | notifee               | Expo 官方，与 EAS 集成                                   |
| 测试    | **Jest + RNTL + Maestro**                                             | —                     | Detox                 | Maestro 是新趋势，写 E2E 像写 YAML                         |
| 监控    | **Sentry + Posthog**                                                  | —                     | Firebase              | Sentry 崩栈捕获 + Posthog 自托管产品分析                      |
| OTA   | **EAS Update**                                                        | —                     | CodePush              | Expo 原生支持                                          |
| 包管理   | **pnpm**                                                              | 9.x                   | —                     | monorepo 友好                                        |

### 2.2 后端（Supabase BaaS + 少量 Edge Functions）

| 层              | 选型                                                | 理由                                       |
| -------------- | ------------------------------------------------- | ---------------------------------------- |
| 数据库            | **PostgreSQL 15+**                                | RLS 是核心保障；JSONB 存加密 payload 灵活           |
| 鉴权             | **Supabase Auth（GoTrue）**                         | 内置 Magic Link / OAuth / WebAuthn；少写 1 个月 |
| 实时             | **Supabase Realtime（Logical Replication）**        | 直接订阅 PostgreSQL；免运维                      |
| 对象存储           | **Supabase Storage（S3 兼容）**                       | 头像 / 截图原图；RLS policy                     |
| Edge Functions | **Deno Deploy**                                   | 与 Supabase 一体；TypeScript；冷启动 < 50ms      |
| 邮件账单解析         | Edge Function + **GPT-4o-mini** 结构化抽取             | 见 [§14.3](#143-邮件账单解析-p1)                |
| 推送桥接           | Edge Function + **APNs HTTP/2** + **FCM HTTP v1** | Expo Push 不存敏感数据，敏感提醒直发                  |

### 2.3 基础设施

| 项        | 选型                                                        |
| -------- | --------------------------------------------------------- |
| 版本控制     | GitHub                                                    |
| CI       | **GitHub Actions** + EAS Build                            |
| 灰度发布     | EAS Update channels（production / staging / internal）      |
| 密钥       | **HashiCorp Vault**（Secret refs） + Expo Encrypted Secrets |
| 域名 + CDN | Cloudflare                                                |
| 状态页      | BetterStack / Instatus                                    |
| 错误预算     | Sentry Release Health                                     |

### 2.4 不选用的清单（也说清楚）

| ❌                     | 原因                                             |
| --------------------- | ---------------------------------------------- |
| Redux                 | 5 年陈旧样板代码，工程效率不如 Zustand                       |
| GraphQL               | 客户端加密聚合场景下，GraphQL resolver 的优势被 RLS REST 完全替代 |
| Firebase              | 中国大陆访问不稳定，APNs/FCM 通道在国内弱；Supabase 可自托管        |
| 原生 Swift/Kotlin 双仓    | 团队规模 < 3 人，ROI 为负                              |
| 后端自建 Node/NestJS      | Supabase 已覆盖 90% 需求，自建后端是重复造轮子                 |
| Tauri/Flutter Desktop | 不在 MVP 范围                                      |

## 3. 性能预算与设计约束

> 不是技术选型能解决的，是「产品承诺给用户」的硬指标。性能预算驱动架构决策。

### 3.1 启动性能

| 指标                       | 预算（M1）                         | 强制保障手段                        |
| ------------------------ | ------------------------------ | ----------------------------- |
| 冷启动至首页可交互                | ≤ **2.5 秒**（Android 中端机）       | Splash + Skeleton + 优先 SQLite |
| 热启动                      | ≤ **600ms**                    | 单进程、状态持久化                     |
| TTI（Time to Interactive） | ≤ **1.8 秒**                    | 代码分割（Expo Router 自动）          |
| JS Bundle 体积             | ≤ **8 MB**（release / 三端去除 dev） | tree-shaking + ASO 资源压缩       |

### 3.2 运行时性能

| 场景               | 预算          | 卡点                               |
| ---------------- | ----------- | -------------------------------- |
| 列表滚动 60fps（资产列表） | ≥ 58fps     | FlatList + `getItemLayout` + 虚拟化 |
| 切换 Tab           | ≤ 200ms     | 复用 Zustand store，避免重新 fetch      |
| 趋势图渲染（10万点）      | ≤ 600ms     | 数据采样 + Canvas 离屏                 |
| OCR 识别一张截图       | ≤ 3 秒       | 后台任务，结果走通知                       |
| 双向同步（10条变更）      | ≤ 2 秒（WiFi） | 批量 upsert + 增量推送                 |
| 端到端加密一次加解密       | ≤ 8ms       | AES-NI 在 iOS/Android 都启用         |

### 3.3 数据规模上限（M1 设计目标）

| 维度      | 上限     | 影响                     |
| ------- | ------ | ---------------------- |
| 单家庭资产条目 | 500    | 趋势聚合可在客户端 ≤ 200ms      |
| 资产快照    | 50万    | SQLite indexed + 客户端聚合 |
| 成员      | 20     | 权限矩阵 O(n²) 仍可接受        |
| 邀请码并发发放 | 1000/天 | Edge Function 异步足够     |

> 超过上限走 [§20.4](#204-性能层) 升级路径：归档冷数据 / 引入服务端聚合 endpoint（但放弃 E2E）。

### 3.4 网络与电量

| 项      | 预算                        |
| ------ | ------------------------- |
| 后台同步频率 | 仅前后台切换时 + 主动拉取；不轮询        |
| 电量消耗   | 60 分钟后台使用 ≤ 3% 电量         |
| 移动数据   | 100 条资产一周同步 ≤ 5 MB（场景压缩后） |

- **依赖方向**：`auth` 可被任何模块依赖；`family`/`asset` 互不依赖；`trend` 依赖 `asset`/`family`；`ocr` 依赖 `asset`；`notification` 依赖 `asset`/`family`。
- **通信方式**：模块间只通过 Zustand store 或 React Query 缓存交互，**不直接 import** 对方的内部组件。
- **错误处理**：每个 feature 暴露 `useXxxErrors()` hook，错误统一走 `<ErrorBoundary>` + Toast。

## 6. 状态管理（Zustand + React Query）

> **分工原则**：Zustand 管「跨页面会话态」；React Query 管「远端数据 + 缓存 + 失效」。本地数据库是单一可信源（single source of truth）。


### 6.1 Zustand stores（持久化策略）

| Store     | 持有                                            | 持久化                  | 重置时机      |
| --------- | --------------------------------------------- | -------------------- | --------- |
| `session` | userId / 当前 deviceId / 会话过期时间                 | AsyncStorage（不含敏感字段） | 退出登录      |
| `family`  | 当前 familyId / 当前角色 / Family Data Key（**仅内存**） | 不持久化（每次启动重新派生）       | 切换家庭 / 退出 |
| `asset`   | 资产筛选条件 / 排序 / 视图偏好                            | AsyncStorage         | 退出登录      |
| `ui`      | 弹窗 / Toast / TabIndex / Skeleton 状态           | 不持久化                 | App 重启    |

```ts
// 写一条资产（典型示例）
async function createAsset(input: AssetInput) {
  // 1) 本地事务
  await db.write(async () => {
    const asset = await db.collections.get('assets').create((r) => {
      r._raw.id = uuid();
      r.familyId = familyId;
      r.encryptedPayload = encrypt(input, fdk);
      r.amountCipher = encryptNumber(input.amount, fdk);
      r.dirty = true;
      r.lastModifiedAt = Date.now();
      r.version = 1;
    });
    await db.collections.get('snapshots').create((s) => {
      s.assetId = asset.id;
      s.amountCipher = encryptNumber(input.amount, fdk);
      s.takenAt = Date.now();
    });
  });

  // 2) 推送到服务端（异步）
  syncQueue.enqueue({ table: 'assets', id: asset.id, op: 'insert' });
}
```

### 9.2 RLS Policies（核心）

```sql
-- supabase/migrations/20260905000002_rls.sql

-- 关键开关
alter table public.profiles       enable row level security;
alter table public.families       enable row level security;
alter table public.family_members enable row level security;
alter table public.invitations    enable row level security;
alter table public.assets         enable row level security;
alter table public.asset_snapshots enable row level security;
alter table public.alert_rules    enable row level security;
alter table public.audit_logs     enable row level security;

-- 工具函数：判断当前用户是否是某个家庭的成员
create or replace function public.is_family_member(p_family uuid)
returns boolean
language sql stable security definer set search_path = public
as $$
  select exists(
    select 1 from public.family_members
    where family_id = p_family
      and user_id = auth.uid()
      and joined_at is not null
      and left_at is null
  );
$$;

create or replace function public.family_role(p_family uuid)
returns text
language sql stable security definer set search_path = public
as $$
  select role from public.family_members
  where family_id = p_family and user_id = auth.uid()
  and joined_at is not null and left_at is null
  limit 1;
$$;

-- profiles: 只能改自己的；所有人可读
create policy "profiles read self or family"
on public.profiles for select using (true);
create policy "profiles update self"
on public.profiles for update using (id = auth.uid());

-- families: 成员可见
create policy "families select members"
on public.families for select using (public.is_family_member(id));

-- family_members: 同家庭成员可见
create policy "members select same family"
on public.family_members for select using (public.is_family_member(family_id));
create policy "members update by owner"
on public.family_members for update using (public.family_role(family_id) = 'owner');

-- invitations: 创建者（owner/editor）可创建；任何登录用户可用 code 兑换
create policy "invitations select members"
on public.invitations for select using (public.is_family_member(family_id));
create policy "invitations insert owner_editor"
on public.invitations for insert with check (
  public.family_role(family_id) in ('owner','editor')
);

-- assets: 同家庭成员可读；owner+editor 可写
create policy "assets select family"
on public.assets for select using (public.is_family_member(family_id));
create policy "assets write owner_editor"
on public.assets for all using (
  public.family_role(family_id) in ('owner','editor')
) with check (
  public.family_role(family_id) in ('owner','editor')
);

-- snapshots: 与 assets 同步
create policy "snapshots select family"
on public.asset_snapshots for select using (public.is_family_member(family_id));
create policy "snapshots write owner_editor"
on public.asset_snapshots for all using (
  public.family_role(family_id) in ('owner','editor')
) with check (
  public.family_role(family_id) in ('owner','editor')
);

-- alert_rules: 同 assets
create policy "alerts select family"
on public.alert_rules for select using (public.is_family_member(family_id));
create policy "alerts write owner_editor"
on public.alert_rules for all using (
  public.family_role(family_id) in ('owner','editor')
) with check (
  public.family_role(family_id) in ('owner','editor')
);
```

## 11. 端到端加密 · 实现细节

### 11.1 密钥层级

```
用户密码
  │
  │ PBKDF2-SHA256（210,000 iterations，OWASP 2024 推荐）
  │
  ▼
User Master Key（UMK，32 字节）
  │
  │ ├─ HKDF（info="local-keystore"）   → 解密设备本地密钥库
  │ ├─ HKDF（info=f"<familyId>")       → Family Data Key（FDK）
  │ └─ 用于 wrapping 邀请时发给新成员
  │
  ▼
Family Data Key（FDK，32 字节）
  │
  │ AES-256-GCM（每条资产随机 IV）
  │
  ▼
密文：encrypted_payload / amount_cipher
```

### 11.2 密钥生命周期

| 阶段           | 存储                               | 持久化方式                           |
| ------------ | -------------------------------- | ------------------------------- |
| 密码           | 不存储                              | 用户每次输入（或用生物识别 guard）            |
| UMK          | **仅内存**                          | App 重启需要重新派生                    |
| FDK          | **仅内存**                          | 退出家庭 / 切换家庭即清空                  |
| 设备 keystore  | Android Keystore / iOS Keychain  | 系统级保护                           |
| 服务端 envelope | `families.encrypted_fdk` (jsonb) | 用 Owner 公钥（RSA-OAEP / X25519）加密 |

### 11.3 加密库选型

| 平台      | 推荐                                     | 备选                        | 备注                            |
| ------- | -------------------------------------- | ------------------------- | ----------------------------- |
| iOS     | **CommonCrypto**（系统原生）                 | CryptoSwift               | Swift Crypto 与 Hermes 已支持 GCM |
| Android | **Tink**（Google 维护）                    | BouncyCastle              | 自动处理 IV / AEAD tag            |
| 跨 RN    | **@noble/ciphers** + **@noble/hashes** | react-native-quick-crypto | Pure JS，体积小，慢 20-50% 但可控      |
| 高性能场景   | react-native-quick-crypto              | —                         | 用 libcrypto / libssl 加速       |

**推荐组合**：RN 主代码走 `@noble/*`（体积小、可审计），核心路径频繁加解密用平台原生（通过 Native Module 暴露）。

### 11.4 代码示例：加密一条资产

```ts
// src/crypto/aes.ts
import { gcm } from '@noble/ciphers/aes';
import { randomBytes } from '@noble/ciphers/utils';
import { utf8ToBytes, bytesToUtf8 } from '@noble/hashes/utils';

export function encryptJSON(plain: unknown, key: Uint8Array) {
  const iv = randomBytes(12);
  const plaintext = utf8ToBytes(JSON.stringify(plain));
  const ciphertext = gcm(key, iv).encrypt(plaintext);
  return { alg: 'AESGCM-256', ciphertext: bytesToB64(ciphertext), iv: bytesToB64(iv) };
}

export function decryptJSON<T = unknown>(env: Envelope, key: Uint8Array): T {
  const iv = b64ToBytes(env.iv);
  const ct = b64ToBytes(env.ciphertext);
  const pt = gcm(key, iv).decrypt(ct);
  return JSON.parse(bytesToUtf8(pt));
}
```

### 11.5 主密码与生物识别双因子

```
登录  ─ 输入主密码 → 派生 UMK → 解密 keystore → 解锁
                                ↓
                               通过
                                ↓
          ┌─────────────────────┴─────────────────────┐
       启用 Face/Touch                            未启用
          ↓                                          ↓
    30 分钟内可解锁，          每次冷启动都需主密码
    期间不需重输
```

**实现**：

- 用 `react-native-keychain` 存 `keystore_wrapped_umk` + 生物识别 guard
- 失败/未启用：强制主密码解锁

### 11.6 密码更换 / 密钥轮换

| 场景      | 策略                                                               | 影响               |
| ------- | ---------------------------------------------------------------- | ---------------- |
| 用户改密码   | 重派生 UMK；用旧 UMK 解密 keystore，重 wrap                                | 仅本地              |
| 家庭换 FDK | Owner 触发：生成新 FDK + rewrap 所有 envelope；推 Realtime 让成员重 wrap 自己的副本 | 全员需在线一次；离线成员需重邀请 |
| 设备丢失    | 远程 revoke：清空 `push_subscriptions`，其他设备下次同步感知                     | 用户感知小            |

### 11.7 收据化存储（用于追加场景）

资产快照表用「追加而非修改」：

```
INSERT INTO asset_snapshots (...)  -- 每改一次插一行
```

这样：

- 加密字段不会被「重加密」破坏一致性
- 趋势图天然是 append-only 流
- 异地多设备容易 merge（按 taken_at 排序）

## 12. 实时同步与冲突解决

### 12.1 三方同步模型

```
设备 A  ─┐          ┌─ 设备 B
          │          │
          ▼          ▼
       ┌──────────┐
       │  服务端   │
       │ (Postgres)│
       └─────┬────┘
             │
             ▼
       设备 C（离线 5 分钟后回网）
```

### 12.2 同步流程（推 + 拉 + 校）

```
本地写入 → sync_queue (dirty=true)
   ↓
[推送] 按 LWW（Last-Write-Wins）策略：
       - 携带 client_version + last_modified_at
       - 服务端 bump server_version 触发 Realtime 广播
   ↓
[拉取] pg_last_wal_replay_lsn() > 上次 LSN：
       - 拉取 server_version > 本地的所有 row
       - 解密、合并到本地（OT 简化版，见下）
   ↓
[冲突解决]
```

### 12.3 冲突解决：CRDT-lite 简化 OT

| 字段               | 冲突时怎么处理                                               |
| ---------------- | ----------------------------------------------------- |
| `name` / 类型      | LWW（按 server_version）                                 |
| `current_amount` | LWW（按 server_version）；客户端若在 v_n 之上有未推变更则合并为新 snapshot |
| 软删除 vs 编辑        | 删除优先（A 删了，B 在离线时改 → 合并为 delete）                       |
| 同一资产并发改          | 客户端把第二份改动存为「pending snapshot」，下次进入录入页提示用户合并           |
| 元信息（成员权限）        | 服务端 reject 重放，返回 409 → 客户端拉最新                         |

> 在加密场景下无法做「字段级合并」，**所以尽量减少冲突 → 提示用户手工处理**是务实做法。

### 12.4 关键不变量校验

- 同一 `asset_id` 不能出现两条 `taken_at` 完全相同的 snapshot（DB 加 UNIQUE 索引）
- `last_modified_at` 与 `server_version` 必须单调递增
- 删除使用 `deleted_at` 软删，便于恢复
- 服务端不为加密字段做 sum / min / max 等聚合（避免侧信道推断）

### 12.5 Realtime 断线感知与重连

```ts
const channel = supabase.channel(`family:${familyId}`, {
  config: { presence: { key: userId } },
});

channel.on('system', { event: 'disconnected' }, () => {
  // 标记网络断；本地继续工作
  setSyncState('offline');
});
channel.on('system', { event: 'connected' }, () => {
  // 触发一次全量 reconciliation
  setSyncState('syncing');
  await syncEngine.reconcile();
  setSyncState('online');
});
```

## 13. 离线优先策略

### 13.1 「以本地为准」原则

任何 UI 操作都先入本地 SQLite，远端同步是 **副作用** 而非前提。即使服务端永远不通，App 仍能完成录入、查看、统计。

### 13.2 离线模式 UX

| 元素    | 在线     | 离线                     |
| ----- | ------ | ---------------------- |
| 顶部状态条 | 隐藏     | 黄条："离线模式 · 变更将在联网后同步"  |
| 保存按钮  | "保存"   | "离线保存"（淡显）             |
| 时间戳   | 显示同步时间 | 显示「本地时间 · 未同步」+ 等同步后切换 |
| 推送    | 实时     | 累积到联网时一次性              |

### 13.3 冷启动同步时序

```
1. 启动 → 读 AsyncStorage 会话 → 拉到当前家庭 familyId
2. 派生 UMK + FDK（需要主密码或生物识别）
3. 拉取本地 SQLite 显示 UI（极快）
4. 后台静默：
   a) 推送 sync_queue 中所有 dirty 行
   b) 拉取 server_version > 本地的最新行
   c) 启动 Realtime 订阅
```

### 13.4 写入离线安全

- 任何写入都 `await` 本地事务完成才返回 UI（用户体验流畅）
- sync_queue 单独表，崩溃恢复也能继续推送
- 长事务切割：每条记录一个事务，避免 1 万条资产批量更新阻塞

### 13.5 存储空间

| 估算            | 大小           |
| ------------- | ------------ |
| 1 千条资产（含快照）   | ~5 MB SQLite |
| 1 万条资产        | ~50 MB       |
| 5 万条资产（M1 上限） | ~250 MB      |

预留 500 MB 给本地 SQLite；超限提示用户归档 / 删除旧资产。

## 19. 安全清单

> 多端多层的零信任策略。客户端被篡改是「假设」，服务端被攻破是「预算」。

| 威胁        | 防御                                                          |
| --------- | ----------------------------------------------------------- |
| **设备丢失**  | 设备 keystore 保护 + 远程撤销 + 自动锁定                                |
| **中间人攻击** | 全链路 TLS 1.3 + Certificate Pinning（Supabase 域名）              |
| **数据库泄漏** | 金额密文存储 + envelope 加密 FDK                                    |
| **密钥泄漏**  | 密码高强度 + PBKDF2 + 失败计数锁定（5 次 → 15 分钟）                        |
| **凭据重用**  | 强制 magic-link + WebAuthn（P1） / 不支持纯密码                       |
| **注入**    | Supabase 参数化 + RLS 阻止跨家庭查询                                  |
| **客户端篡改** | Hermes Bytecode + Play Integrity（Android）/ DeviceCheck（iOS） |
| **侧信道**   | 服务端不做加密字段聚合；客户端常量时间字符串比较                                    |
| **备份泄漏**  | 自动备份加密 + 双人审批下载                                             |
| **钓鱼**    | 自定义域 OTP 邮件（jiazi@example），SPF/DKIM/DMARC 全配                |

### 19.1 合规

- **个保法 / GDPR**：隐私政策 + 数据导出 + 一键删除（需 P1 跟进）
- **金融**：不属于金融机构，但建议避免使用「理财 / 投顾」字眼
- **应用商店**：Apple 4.0 / Google 4.0 隐私清单 + 数据使用说明
