# 家庭资产管理 App — 鸿蒙适配方案评估

**文档版本**：v1.0
**创建日期**：2026-09-05
**关联文档**：`家庭资产管理App-需求定义.md` v2.1

---

## 一、决策背景

2026 年 9 月，**HarmonyOS NEXT** 已正式商用，纯鸿蒙内核、**不再兼容 Android APK**。

- 鸿蒙在国内手机市场份额已突破 **17%**（Counterpoint 2026 Q2 数据）
- 华为应用市场月活用户 **5.8 亿+**
- 华为设备出货量持续走高，2026 年预计 **1.5 亿台**

**核心问题**：RN 主版本代码**无法直接打包**为鸿蒙 NEXT 包，必须显式选型。

---

## 二、三个候选方案

### 方案 A：双轨并行（Native + ArkTS 独立实现）

| 维度 | 详情 |
|---|---|
| **架构** | RN/Expo 出 iOS + Android；**另起一套 ArkTS** 出 HarmonyOS NEXT |
| **代码复用** | 业务模型层用 TS 写一次，前端 UI 双端实现 |
| **人力** | RN 工程师 2 人 + ArkTS 工程师 1 人（或 RN 工程师 1 人转岗学 ArkTS） |
| **工期** | 主版本 12 周 + 鸿蒙版额外 **+3 周** |
| **人力成本** | ×1.3 ~ ×1.5（按 6 个月算，多花 ¥18 万 ~ ¥36 万） |
| **UI 一致性** | 两套实现，需建立 design system 规范 |
| **维护成本** | 高：bug 修复、新功能需两端同步 |
| **优势** | 快速覆盖鸿蒙用户，吃华为生态红利；性能最优 |
| **劣势** | 人力翻倍；UI 双倍工作量；长期维护负担重 |

### 方案 B：观望迁移（等待 RN-HarmonyOS 成熟）

| 维度 | 详情 |
|---|---|
| **架构** | 全部依赖 **RN-HarmonyOS** 社区方案 |
| **代码复用** | 一套 RN 代码，三端共享 |
| **人力** | RN 工程师 2 人，无增量 |
| **工期** | 主版本 12 周，无延期 |
| **人力成本** | ×1.0（无增量） |
| **UI 一致性** | 一套代码天然一致 |
| **维护成本** | 低 |
| **优势** | 节省人力；长期 ROI 最高；技术栈统一 |
| **劣势** | **RN-HarmonyOS 仍处于早期**（截至 2026.9，第三方库覆盖率约 60%）；部分功能（如相机、推送）需 native bridge；**错过鸿蒙先发用户红利** |

### 方案 C：渐进混合（推荐）⭐

| 维度 | 详情 |
|---|---|
| **架构** | MVP 阶段 **只做 iOS + Android**；M2 阶段同步启动 ArkTS 原生版，**只覆盖 P0 功能** |
| **代码复用** | 业务模型层、数据层、API 层 TS 共享；UI 层独立 |
| **人力** | MVP 阶段 2 人 RN；M2 增加 1 人 ArkTS（可外包） |
| **工期** | MVP 12 周；鸿蒙版 M2 再 +4 周（功能 < 主版本） |
| **人力成本** | ×1.0（MVP）→ ×1.2（M2） |
| **UI 一致性** | MVP 一致；M2 后两套但功能子集 |
| **维护成本** | 中：核心功能双端，长尾功能单端 |
| **优势** | **MVP 不延期**；用真实数据验证产品价值后再决定鸿蒙投入；现金流友好 |
| **劣势** | M2 阶段需协调双端；可能错过 6 个月鸿蒙红利窗口 |

| 评估维度 | 方案 A 双轨并行 | 方案 B 观望迁移 | 方案 C 渐进混合 ⭐ |

## 四、决策建议

### 推荐方案 C（渐进混合）

**核心理由：**

1. **产品价值未验证前不投入鸿蒙资源**
   - 当前 MVP 还在验证"家庭资产管理"是否真有用户痛点
   - 把有限资源压在一个未验证的市场是赌博

2. **现金流友好**
   - 创业早期每分钱都要花在刀刃上
   - MVP 阶段先跑通 iOS + Android 主版本
   - 看到真实用户增长后再追加鸿蒙投入

3. **RN-HarmonyOS 在 6-12 个月内会显著成熟**
   - 2026 Q4 预计第三方库覆盖率达 **75%**
   - 2027 H1 预计 **85%+**
   - 越往后，等的代价越小

4. **鸿蒙用户分阶段覆盖不影响核心业务**
   - 家庭资产管理是低频工具，用户不会因为"鸿蒙没版"就流失
   - 核心是 iOS + Android 用户先用起来

### 何时启动方案 C 的 M2 鸿蒙开发？

**触发条件（任一即启动）：**

| 触发条件 | 数据来源 |
|---|---|
| iOS + Android 月活 > **5,000** | 自有数据 |
| 用户主动反馈"何时出鸿蒙版"超过 **50 条** | 应用商店评论 + 客服 |
| 鸿蒙在国内份额突破 **25%** | Counterpoint / IDC 报告 |
| 已有大客户（B 端/家庭批量）要求鸿蒙支持 | BD 反馈 |

**预算上限**：鸿蒙版 M2 总投入不超过主版本的 **30%**（约 ¥18 万 / 4 周）。

## 五、方案 C 的具体落地路径

### Phase 1（M1，Week 1-12）：主版本

```
RN + Expo
├─ iOS (15.0+)
├─ Android (8.0+)
└─ 业务模型层 / 数据层 / API 层（TS 共享）
```

**交付**：
- App Store + Google Play 上线
- 核心 11 类资产管理 CRUD
- 趋势图、家庭协作、权限分级

### Phase 2（M2，Week 13-20）：鸿蒙版启动

**触发**：Phase 1 跑满 4 周、数据验证后启动

```
ArkTS 原生（独立仓库）
├─ HarmonyOS NEXT (API 12+)
├─ UI：复用设计稿（鸿蒙设计规范适配）
└─ 数据/网络：调用 Phase 1 同一后端 API
```

**P0 功能覆盖**：
- ✅ 资产录入（11 类）
- ✅ 总资产仪表盘
- ✅ 趋势图
- ✅ 家庭协作邀请
- ⏸ OCR、异动提醒、API 接入延后到 M3

**人力**：
- 主版本 2 人继续维护 iOS + Android
- 鸿蒙版招 1 名 ArkTS 工程师（或外包给华为生态合作伙伴）

### Phase 3（M3+）：长期演进

**视情况二选一**：

- **如果 RN-HarmonyOS 成熟（>85% 库覆盖）**：考虑把鸿蒙版迁移回 RN 主版本，统一代码库
- **如果鸿蒙用户占比 > 25%**：保留双轨，投入更多人力做功能同步

## 六、风险与预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| RN-HarmonyOS 进展不及预期 | 中 | Phase 3 无法合并代码 | 维持双轨即可（已是 Plan B） |
| 鸿蒙版 M2 用户量 < 预期 | 中 | 投入回报低 | 收窄维护范围，仅做安全更新 |
| ArkTS 工程师招聘困难 | 高 | M2 延期 | 提前 4 周启动招聘；备选方案：外包给华为 ISV |
| 双端 UI 同步出现分歧 | 中 | 用户体验不一致 | 严格 design system 规范；UI 评审制 |
| 鸿蒙份额突破更快（>25%） | 低 | 错过红利 | 加速 M2，可压缩到 +2 周（牺牲部分 P1 功能） |

---

## 七、最终建议

> **采用方案 C（渐进混合）**：
>
> - **MVP 阶段不做鸿蒙**，集中资源打磨 iOS + Android 主版本
> - **M2 阶段根据真实数据决定**是否启动鸿蒙版
> - **长期视生态成熟度决定**是否合并代码库
>
> 这一策略既控制了风险，又保留了灵活性，是绝大多数早期团队的最佳选择。
